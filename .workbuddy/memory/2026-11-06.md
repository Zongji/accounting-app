## 记账应用规划方案（对话产出，尚未开工）

需求：多账本 → 每账本多账户 → 每笔流水一对一绑定某个账户；云服务存储；手机 + PC 响应式。

关键设计决策：
- 表：books / accounts / categories / transactions / transfer_groups，全部 owner_id TEXT DEFAULT auth.uid() + RLS。
- 金额统一用 BIGINT 存「分」，不存浮点；账户余额不落库，由 initial_balance_cents + SUM(流水) 经 PostgreSQL 函数计算，后续可加月度快照。
- 「转账」与「流水一对一账户」冲突的解法：一次转账 = 同一事务内生成两笔流水（transfer_out / transfer_in），共享 transfer_id，每笔仍只绑定一个账户；报表按 transfer_id 抵消，避免内部转账重复计入收支。
- 多表写入（转账、整组删除、账本归档）走 PostgreSQL RPC 单事务；client_token 唯一约束做幂等防重复提交。
- 云服务选型（默认）：WorkBuddy 托管 Cloud Service，Auth + Database + Storage 三模块，SDK @tencent-ai/workbuddy-cloud-sdk@dev，配置全部取自 publicConfig；静态托管无 history fallback → HashRouter，OAuth 回调必须落在站点根路径。
- 备选：自建 Spring Boot + PostgreSQL + 对象存储（贴合用户 Java/Spring Cloud 背景），数据模型与前端不变，仅替换数据访问层。
- 前端默认：Vite + React + TS + Tailwind + TanStack Query + Zustand。响应式单代码库：<768px 底部 Tab/单列卡片/FAB，≥1024px 左侧账本导航 + 中间表格 + 右侧统计。

待用户拍板：是否共享账本（影响 RLS，建议放 V2）、是否多币种、托管云服务还是自建 Spring Boot、登录方式、是否要离线记账。

状态：仅规划，未创建任何应用代码、未激活云服务环境。工作区当前为空目录。

## 方案修订（同日，用户明确纠正模型）

用户确定采用「一笔流水关联 1 或 2 个账户」，推翻上面的「转账拆成两笔流水」设计：
- 单独支出 / 收入流水：只关联 1 个账户；转账流水：关联 2 个账户（转出 + 转入）。
- transactions 字段：account_id NOT NULL（主账户）+ counter_account_id NULL（对手账户，仅转账有值）+ type(expense/income/transfer) + amount_cents BIGINT 恒为正，方向由 type 决定；可选 fee_cents 从转出方额外扣。
- 数据库 CHECK 约束强制：type IN ('expense','income') → counter_account_id IS NULL；type='transfer' → counter_account_id 非空且 <> account_id。外键/触发器保证两账户与流水同账本。
- 移除 transfer_groups 表；转账是一条记录，编辑/删除天然原子，不再需要双行事务。
- 余额计算改为按 type 分支的 PostgreSQL 函数；转账不计入收入/支出报表，避免虚增。
- 账户维度流水查询需 account_id = X OR counter_account_id = X，建议两个部分索引（或表达式索引）。
- UI：记账表单按 type 切换单账户 / 双账户选择器；明细里转账显示「招行卡 → 微信钱包」。
- 跨账本转账 V1 仍不做（两账户必须同账本）。

云服务选型、响应式断点、分期路线不变。状态仍为规划阶段，未开工。

## 账本与账户关联（用户追问并确认）

- 采用一对多：accounts.book_id BIGINT NOT NULL REFERENCES books(id)。账户记录本身归属账本，不是「全局账户池 + 多对多关联表」。
- 每个账本有各自独立的账户配置：账户清单、期初余额、币种、是否计入总资产、排序、图标颜色、信用卡额度、归档状态，全部是 accounts 行上的字段。
- 不同账本允许同名账户（如都有「微信钱包」），是两条独立记录、独立余额；唯一约束用部分索引 UNIQUE(book_id, name) WHERE archived_at IS NULL。
- 两层隔离：RLS owner_id（用户级）+ book_id（账本级）；前端所有查询必须带当前账本 book_id，不能只靠 owner_id。
- transactions.book_id NOT NULL，触发器校验 account_id / counter_account_id 所指账户的 book_id 与流水一致。
- 新建账本可从内置模板初始化一套默认账户，之后各自独立演化；账本软删除时其账户/分类/流水一并归档。
- 不需要 accounts ↔ books 中间表（那会导致余额归属模糊，与「独立配置」语义冲突）；跨账本转账因账户不共享，V1 不支持。
